# AGENTS.md

Guidelines for AI agents (Claude, Gemini, GPT, Codex, etc.)

## Overview

VS Code extension that renders 3D model files (`.babylon`, `.glb`, `.gltf`, `.gltf2`, `.obj`, `.stl`, `.ply`, `.splat`, `.spz`) using Babylon.js. It contributes (besides adding `.babylon` / `.gltf` / `.gltf2` to the built-in `json` language, so the text editor treats them as JSON):
- A **3D editor** in a webview: a 3D view (camera framed on the model — skinned meshes by their posed bounds, glTF models from the front since they face +Z; the player has a view bar at the top of the view — Reset view first, then render mode buttons textured / solid (Babylon's global `MaterialFlags.*TextureEnabled` off) / wireframe (the meshes get a shared line material for the time of the view — thin lines of a gray that stands out from `scene.clearColor`, not the mesh material), a vertices toggle (points over any mode: orange helper meshes `__editorVertices` sharing the geometry, skeleton and morph targets of the model meshes, on `VERTICES_LAYER`, depth-tested so points behind polygons are hidden; made only while a shown view shows them), a normals toggle (a line along the normal of every vertex, skinned like it is drawn — `getPositionData` / `getNormalsData` with the skeleton prepared for the frame —, on `NORMALS_LAYER`, depth-tested) and a bone axes toggle (X red / Y green / Z blue at each joint, the world matrix of the bone — its linked node, else the bone in the space of its mesh —, on `BONE_AXES_LAYER`, drawn over the model like the bones), both line systems made again every frame while a view shows them (`setNormalsNeeded` / `setAxesNeeded`, the toggles are `ViewOverlay`s of `Toolbar.setOverlays`), view only (`ViewRendering`: `beforeView` / `afterView` around each view, the model keeps its materials), then the mesh / bones toggles; the cursor modes View / Edit are in the toolbar above, after the view switch, for every view at once (V / W·E·R, `Editor._setCursor`, kept in the webview state — a `select` mode kept by earlier versions becomes Edit; in Edit the cameras of the views turn with the middle button — `CameraViews.setSelectMode` sets the buttons of their pointer inputs; Edit shows the tools Move / Rotate / Scale: `TransformEditing` puts Babylon's gizmo (in a utility layer drawn with the camera of the view under the pointer) at the centre of the selection — the top-most selected bones of a table with a `poseEdit` (skeleton inspector: its Rest or Bind pose, clip inspector: keys at the shown frame — `writeLocal`) while the view shows the bones, else the selected vertices of the mesh shown (their drawn positions moved, found back through the inverse of the world and of the blended skin matrix of each vertex; vertices at the position of a selected one move with it; the normals of the vertices of the triangles they are in are made again — area-weighted faces of each vertex, on the side the normal had); a Local axes toggle (X) turns the gizmo to the axes of the first selected bone, or of the mesh (`setLocal`, kept in the webview state); a drag applies live, then the start state is put back and the end state recorded by the history as one undo step; a click on the gizmo is no selection); the selection rectangle (`BoxSelection`: the left button draws it in Edit; it selects the joints of the bones of the shown skeleton — without a bone table in the inspector the skeleton inspector opens with them (`Editor._selectBones` / `_openWithSelection`, also for Shift+click on a bone) —, else the vertices of the mesh the inspector shows, or, when it shows none or none of its vertices are inside, of the visible mesh with the most vertices inside, opened with them (`_pickableMeshes`: drawn by the camera of the view) — only those no triangle of a visible mesh hides, unless the view shows lines (`ScreenSelection`: the drawn, skinned positions projected into the view under the pointer — Babylon's viewports count from the bottom —, triangles sorted into 32 px cells, 1 / depth interpolated on the screen); Shift adds, Option / Alt takes out — also for a click on a bone or a vertex; a click on a vertex of another mesh opens that mesh with it in Edit or while the view shows the vertices (`ScreenSelection.nearestVertexIn`); `PropertyPanel.selectObjects`), Reset view all for the **selected** view (a click on its canvas or its camera tag selects it, framed with more than one view; `CameraViews.settingsOf` / `setSettings`: the settings belong to the camera of the view, by ref, and move with it; the base cameras default to lines with vertices; kept in the webview state with the views): the render mode of each view is applied before it is drawn and undone after it (`scene.onBefore/AfterCameraRenderObservable` → `ViewRendering`, the texture flags change only when the mode does), the mesh / bones of each view in skeleton mode through the layer mask of its camera (`CameraViews.applyMasks`: `MODEL_LAYER` for the model, `BONES_LAYER` for the bones helper of `SkeletonView`; a view that hides the bones does not pick them) — and a playback bar at the bottom — auto-orbit (off on open), play/pause, a seek slider — with tags above it on the right: the mesh and the skeleton the current clip animates, then the clip (with the clip icon of the tree, `clipIcon`) (`Editor._showClipTags`, `ClipFrameEditor.skeletonOf`; the mesh tag names the mesh the skeleton deforms, the node of its parts or the first one `+N` — `meshTag`; none for clips of nodes only); a click on a tag shows its object in the inspector and selects it in the model tree (`Editor._openTag`: `ModelTreeBridge.find` gives the item with its section, `{ type: 'treeReveal', nodes, select }` makes the host reveal it — `ModelTreeProvider._reveal`; a mesh below a root node opens in its own inspector, back to the root node, which is revealed without selecting); the mesh / bones toggles are shown in skeleton mode and whenever the current clip animates a skeleton — outside skeleton mode they show its bones (the mesh toggle hiding the mesh too), `Editor._toggleSkeletonDisplay`; the toolbar above switches the view with icon buttons — Desktop (both), Model, Inspector, kept for the next opened files; a click on Desktop shows it with the last layout and opens a menu of layouts drawn as svg icons on a 3×2 grid (`layoutIcon`: the inspector on the left or the right, 1 to 4 camera views in the 2×2 cells next to it — one: all, two: top / bottom, three: top and two below, four: 2×2; `Editor._layout`, kept like the view, the workspace gets `workspace--inspector-left` and `PanelResizer.side`); with more than one camera a click on Model shows the model alone with its last camera and opens a menu (`Toolbar.setCameraCount`) of the camera to show it with. The camera views are `CameraViews` (`src/editor/CameraViews.js`): `scene.activeCameras` with viewports, the view under the mouse gets the mouse controls and the picking (`cameraToUseForPointers`), each view has an icon of the world axes (top left, X red / Y green / Z blue, turned with its camera each frame — `createAxesIcon`) and a camera tag (top right) whose menu chooses its camera (a camera shown elsewhere changes place) or shows it in the inspector; cameras of the file are shown through copies (`__editorView:<id>`, made again when the file camera changes — `refreshCopies` after every edit — or the model reloads), so moving a view never changes the file; Reset view resets the camera of the selected view: the preview and base cameras to their framed position (`CameraController.resetView(camera)`), a file camera to the file values, a virtual camera to its values when created; the views and the virtual cameras are kept in the webview state (`cameraViews`); only the preview camera auto-orbits) next to a resizable inspector on the right (its header — kind, name, back button — stays, the rest scrolls, in collapsible groups: Properties, Other file fields (collapsed by default), the table; object values of the file such as `producer` are their own group). Below 500 px Desktop is hidden and the last single view is shown; below 400 px of height the layouts with 3 and 4 camera views are not offered and a chosen one is shown with 2 views (`SHORT_HEIGHT`, the choice is kept); when the model view next to the inspector is narrower than its player bars in one line (`Editor._playerWidth`: the wider bar at min-content, measured while shown, re-checked after a model load, a selection and a splitter drag), Desktop is hidden and the model is shown alone until it fits again. The view, the render mode and the UV layout (shown, color) are kept in the panel state and, through `{ type: 'viewSettings', settings }`, in the host's `globalState` (`babylonEditor.viewSettings`), passed to new webviews as `payload.viewSettings`: a newly opened file starts with the last chosen view. There are no separate view/edit modes. `.babylon` files use `babylon-editor.textEditor` (`src/components/BabylonTextEditor.js`, a **custom text editor**: the text document is the single source of truth, see *Document sync*). `.glb`, `.gltf`, `.gltf2`, `.obj` and `.stl` open in `babylon-editor.editor` (`src/components/BabylonEditor.jsx`), which converts them to a `.babylon` document and hands over to the text editor (see *Converted models*); `.ply`, `.splat`, `.spz` (and models whose text would exceed ~48 MB) stay in this binary custom editor, which regenerates the file on save.
- A **compact text view** of `.babylon` files (`babylon-editor.openCollapsedText`, "Open as Compact Text"): `src/components/BabylonTextProvider.js` is a `FileSystemProvider` for the `babylon-text` scheme (`babylon-text:<path>?<real file uri>`) that serves a live projection of the raw text document: vertex buffers, animation `keys` and long strings are replaced by `"…#12"` placeholders (`src/utils/collapseBabylon.js`; a placeholder refers to the value by its JSON path, its text is read from the raw document), the rest is formatted JSON. A CodeLens / hover link expands a placeholder in place. A `.babylon` file opened in a plain text editor is replaced by this view (setting `babylonEditor.collapseTextEditor`, on by default; the extension activates `onLanguage:json` for that) unless it was opened with `babylon-editor.openRawText`; the editor titles of the three views (raw text, compact text, 3D editor) have buttons to open the other two (`openRawText`, `openCollapsedText`, `openInModelEditor`), replacing the active tab (`BabylonTextProvider._switchView`).
- A **Babylon Model** view in the Explorer sidebar (`babylon-editor.modelTree`, shown while a Babylon editor is active via the `babylonEditor.active` context key) with the model tree of the active editor; selecting an item opens it in the inspector. Clips are picked there too: the clip inspector has a **Play** action (always enabled; it makes the clip current and plays it from the start, and turns into **Pause** while this clip plays). In the 3D editor editing happens through UI controls, never through text edits; saving regenerates the file in its original format.

## Commands

```bash
npm run build      # full production build into dist/ (runs clean → js → editor → css → copy:codicons → copy:assets)
npm run watch      # build once, then run all watchers concurrently (esbuild --watch + sass)
npx eslint src     # lint (no "lint" npm script; config matches **/*.js only, so .jsx files are skipped)
```

There are no tests yet: `.vscode-test.mjs` targets `test/**/*.test.js`, but neither the `test/` directory nor `@vscode/test-cli` (and therefore `npm test`) is set up.

Individual build steps live as separate npm scripts (`build:js`, `build:js-editor`, `build:css`) — use them to rebuild a single target instead of the whole pipeline.

To run/debug the extension: press F5 in VS Code (uses the "Run Extension" launch config in `.vscode/launch.json`, which loads the extension from the workspace folder; `.vscode/` is gitignored, the README shows the config). The extension entry point is `dist/extension.cjs`, so **you must build (or watch) before launching** — VS Code loads bundled output, not `src/`.

## Build architecture

Source is authored as **ESM** (`"type": "module"` in package.json) and bundled with **esbuild** into two targets, each with a different runtime environment:

1. **Extension host** — `src/extension.js` → `dist/extension.cjs`. Bundled as CJS for Node, with `vscode` marked external. This is the code that runs inside VS Code's extension host process.
2. **Editor webview** — `src/editor.js` → `dist/js/editor.js`. Runs in the browser sandbox of the custom editor. Uses `@babylonjs/core` directly (raw `Engine` + `Scene`).

`src/editor.js` is the webview entry point (`Editor` wires everything together); its modules live in `src/editor/`:
- Babylon-agnostic UI widgets: `Toolbar`, `PropertyPanel` (typed property editors + actions + table; content with `curves` gets a Table / Graph view switch; `lists` are accordion groups after the main properties — an entry's properties and actions are rendered when it is opened, and opening one closes the open entry of any list; an entry `toggle` is a small button at the end of its header line, e.g. the eye that hides a part in the 3D view through its layer mask without changing the model — `Editor._setHiddenInView`; hidden parts and the open entry (by list and label, `_openKey`) survive a reload of the model; the `image` property type shows a preview, its `get` may return a promise — so may the `get` of a `readonly` one, shown when it resolves; its `menu` actions open in a `PopupMenu` by a click, right click or Enter on the image, its `overlay` is an image laid over it), `DataTable` (virtualized table with cell editing; the bones after it move up, its children hang from its parent with its bind / rest / timeline keys composed in (child × deleted, at the frames of both), its vertex weights go to its parent (to the other influences of a vertex for a root bone), the influences are written expanded (`matricesIndicesExpanded`) in the mesh or its shared geometry, its linked node is removed — the nodes below it hang from its parent with its transform and their animation group keys composed with its keys, its own tracks are removed) with a Rest | Bind switch — `table.modes` — and a Rest pose / Bind pose button next to it — `table.actions`; rest values are editable; bind values are editable too, with a warning notice (`table.noticeWarning`) and a **Move children** toggle — `AnimationController.setBindMatrix` either moves the child joints with the bone or recomputes their local bind matrices so they keep their place; bind undo snapshots the whole skeleton (`captureBind` / `restoreBind`); a bone is renamed by editing its name tag — a `text` column — which also renames the linked glTF node), bone (opened by picking a bone when the inspector has no bone table), clip), `ClipFrameEditor` (clip inspector: transforms of all animated bones/nodes at a selected frame — `.babylon` bone matrices and glTF position/rotation/scaling tracks are shown uniformly as position / rotation° / scaling; editing a frame without a key inserts one with the interpolated value; while the clip plays the graph marks the playing frame — `Editor` calls `PropertyPanel.updateCurrentFrame()` after each render — and picking a frame (a click on a graph lane or key, the Frame property) pauses playback; pausing or seeking while paused makes the stopped frame the inspector frame — `Editor._syncClipFrame`; the zoom sliders do not pause), `ModelSerializer` (writes the model back).

Widgets never mutate the model: property descriptors and table columns carry `get`/`set` (and optional exact `capture`/`restore` snapshots), and `Editor` turns every commit into an `EditHistory` command. Descriptors/actions flagged `transient` (e.g. the clip frame, Play animation) are editor state: they bypass the history and stay enabled for view-only formats.

`DataTable` shows each record as a block: `leading` columns (index) on the left, an optional `title` column as a tag line above the values (the bone name in the clip table), and value columns sharing the width in lines of at most three values; a new `group` (e.g. position / normal / uv) starts a new line. The header is a single line: each value slot lists the labels of its column in all lines, separated by `/` (e.g. `PX/RX°/SX`). A table with `groups` (clip: position / rotation / scaling; vertices: position / normal / uv) gets a switch above it in `PropertyPanel` and shows only the chosen group (the first by default; the choice is kept while switching objects).

`PanelAction` buttons show a short `label` (e.g. Play, Prev, Next) and the full description in `title` (the tooltip); `label`, `title` and `icon` may be functions re-read on refresh.

SCSS in `src/scss/` is compiled by `sass` then bundled by esbuild into `dist/css/`. `copy:codicons` copies the `@vscode/codicons` font and CSS to `dist/codicons/` (the webview can only load files from `dist/`). `copy:assets` copies `public/*` to `dist/` (the `public/` dir may not exist — the script tolerates that).

## Custom JSX runtime (important)

This project does **not** use React. `src/utils/jsx-runtime.js` implements a minimal JSX runtime (`jsx`/`jsxs`/`Fragment`) that renders JSX **directly to HTML strings**. It is wired up via:
- `package.json` build: `--jsx=automatic --jsx-import-source=./utils`
- `jsconfig.json`: `"jsxImportSource": "../utils"`

Consequences when editing `.jsx` files (`BabylonEditor.jsx`):
- JSX expressions produce **strings**, not virtual DOM. `_getHtmlForWebview` returns the HTML for a webview by evaluating JSX.
- `className` is mapped to `class`; all other prop names are lowercased. `on*` handlers and function-valued props are **stripped** (no event binding — this is server-side HTML generation only).
- There is no reconciliation, state, or hooks. Do not import React or React patterns.

## Runtime data flow

- **Content Security Policy**: every editor webview page (`BabylonEditor._getHtmlForWebview`, `contentSecurityPolicy`) allows scripts only with the page's `nonce` plus `'wasm-unsafe-eval'` and `https://cdn.babylonjs.com` (Babylon's Draco / meshopt / KTX2 decoders, loaded into blob workers), styles from the webview resource origin and inline, images / fetches / media from the resource origin, `data:` and `blob:` (and the CDN), workers from `blob:` and the CDN. A new `<script>` needs `nonce={nonce}`; a resource from another origin must be added to the policy. The splat loader would load `fflate` from unpkg.com: the bundled copy is set as `window.fflate` in `src/editor.js`.
- **Custom editor (extension host → webview)**: the HTML injects only metadata, `window.payload = { type, mimeType, fileName, rootUrl }`, where `rootUrl` is the webview URI of the model folder (relative textures/`.bin`/`.mtl` resolve against it; the workspace folder is in `localResourceRoots`). The model bytes are sent by `postMessage` as `{ type: 'loadModel', data: ArrayBuffer }` in reply to the webview's `{ type: 'ready' }`, and as `{ type: 'reloadModel', data }` on revert. `src/editor.js` wraps the bytes in a `File` named `fileName` (the `.babylon` loader cannot read an `ArrayBufferView`) and loads it with `LoadAssetContainerAsync`.
- **Host services**: `WebviewFiles` (`src/components/WebviewFiles.js`, set up by `setupWebview` for every editor webview) answers `saveFile` / `openFile` (dialogs starting in the model folder), `readClipboard` / `writeClipboard` (text, `vscode.env.clipboard`) and `showMessage` with `{ type: 'hostReply', requestId, result | error }`; images are written to the clipboard by the webview (`navigator.clipboard`, PNG only), clipboard images are read there too, falling back to the text read by the host.
- **Model tree (Explorer)**: `src/components/ModelTreeProvider.js` is a `TreeDataProvider` on the host; the data stays in the webview. Sections only expand; model objects run `babylon-editor.tree.click` (a click on the shown item goes back to the file view, `{ type: 'treeSelect', id: null }`; the inspector header has a back button; both clear the tree selection with `list.clear`, focusing the tree first for the back button — the API has no deselect; `getParent` supports `TreeView.reveal`). The context menu (`contextValue` `section:<name>` / `item:<kind>`) has Add… on sections and Rename… / Delete on objects, Copy on nodes, skeletons and clips and Paste on the Nodes, Skeletons and Animations sections (`ModelTreeProvider._copy` / `_paste`: the webview returns `{ kind, value }` — `ModelEdits.copy`: a clip as its tracks with the keys of its window moved to frame 0, window edges keyed with the value Babylon plays there, targets by bone / node name (`CopiedClip`; a model keeps one kind of clips: a frame range of the timeline is pasted as keys appended one frame after the last key of the timeline plus a new range on the owners — the skeleton, animated nodes —, an animation group as a new group; a clip of the other kind is converted by `ClipConverter` — group → range: the position / rotation / scaling tracks of each joint node become one `_matrix` track of the bone of the same name keyed on every frame (Babylon steps matrices between keys), missing channels from the bone's rest pose; range → group: each matrix key is decomposed into position / rotationQuaternion / scaling tracks of the node of the same name —, after the host asked `{ choose: 'channels', title }` — asked for a converted clip and for a clip of another skeleton (the copy carries the rig of its skeleton, `CopiedClip.rig`: bone names, parents, local rest matrices, the world matrix of the space of root bones; not asked when pasted onto its own skeleton in the same file): **Retarget** (`ClipRetarget`: every bone keeps, against its rest pose, the world rotation the source bone has against its own — the rest poses play as each other, so different bone axes, armature rotations and units are handled; positions move from the target rest by the source's move from its rest, turned into the target parent space and scaled by the size of the skeletons (bone lengths stay the target's, root moves keep their stride); scalings stay the target's; matched by bone or linked node name, assumes matched bones have matched parents and the models face the same way at rest; done in the clip's own kind after mirroring — the rig is mirrored with a half turn, the `__root__` convention — before the kind conversion), all channels or rotations only (positions and scalings of the rest pose); a clip copied from a mirrored space (`CopiedClip.mirrored`: the world matrix of the space has a negative determinant, as under the glTF `__root__` node) pasted into a not mirrored one, or the other way, is mirrored along Z (`S·M·S`; position z, quaternion x / y negated); with several skeletons the webview answers `{ choose: 'skeleton', options }` and the host asks; the paste reports the tracks without a target); a skeleton in the `.babylon` format, or a node with the hierarchy below it, its meshes with their own vertex data (no shared geometry), their materials and skeletons (`CopiedNodes`, `parentId` by the parent's id), written with `babylonJsonReplacer`, without runtime unique ids (the loader links meshes by `materialUniqueId` / `skeletonUniqueId` and parents by `uniqueId` first) and the frame 0 key Babylon adds while playing — and the host keeps it in the system clipboard as JSON marked `format: 'babylon-editor.object'` with the `source` document, so it pastes into the same or another model, also in another window; `ModelEdits.paste` gives the copy a free name (`<name> copy`) and new ids; pasted into the file it was copied from (`sameFile`), a node copy keeps its parent and shares the materials and skeletons, else it becomes a root node with copies of them; bone links to missing nodes are dropped; in a `.babylon` text new nodes get free `uniqueId`s of the document (`BabylonJsonBinding.nextFileUniqueId`) for `parentId`, and all inserts go in as one undo step — `BabylonTextEditor._mergeInserts` makes the inserts into one array one change; a pasted skeleton is bound to no mesh — meshes refer to skeletons by `skeletonId`; glTF animations belong to animation groups and are not copied with the skeleton); the host asks for the type, name, image or confirmation and sends `{ type: 'treeCommand', op, … }`; `ModelEdits` (`src/editor/ModelEdits.js`) does the edit — `.babylon`: renames are patches, add / delete are `{ type: 'documentOps', ops }` (array items inserted / removed, references cleared) written by `BabylonTextEditor._writeOps` as one undo step, then the model reloads; other formats: undoable scene commands. Changed items are decorated like changed files (`resourceUri` with the `babylon-tree` scheme and a `FileDecorationProvider`: M / A): for `.babylon` the host compares the object with the saved file by id (`BabylonTextEditor._changeState`), other formats mark changed objects in the webview until saved (`documentSaved`). The host requests children with `{ type: 'treeRequest', requestId, parentId }` (null for roots) and the webview answers `{ type: 'treeItems', requestId, items }`; selection is sent as `{ type: 'treeSelect', id }`. The webview posts `treeReset` after loading a model and `treeChanged` after edits/undo/redo; the provider refreshes only for the active editor panel (the last active one while it stays visible).
- **Edits and undo/redo (binary formats)**: the webview keeps the undo stack (`EditHistory`) and posts `{ type: 'edit', label }` per command; the host fires `onDidChangeCustomDocument` with `undo`/`redo` callbacks that post `{ type: 'undo' }` / `{ type: 'redo' }` back. The model bytes are **not** sent per edit.
- **Save / Save As / backup (binary formats)**: the host posts `{ type: 'getFileData', requestId, format?, producer? }`; the webview serializes the scene (`Editor.serialize`: `ModelSerializer`, or `ModelConverter.writeBabylon` for `.babylon`) in `format` (default: the file's own; Save As takes the extension of the chosen file, `ConvertedModels.saveAsType`, and confirms what the format drops) and replies `{ type: 'fileData', requestId, data }` or `{ ..., error }`. The first save in a session asks for confirmation because the file is regenerated (exporter metadata, numeric precision and formatting change; a re-saved `person.babylon` grows from ~21 MB to ~46 MB). Backups are restored in `openCustomDocument` via `openContext.backupId`.
- **Document sync (`.babylon`)**: the raw `TextDocument` is the only state; the 3D views (several per document: split works), the raw text and the compact view show it live, with one undo stack, one dirty state and one save (the text is saved as is, not regenerated).
  - *3D → text*: the webview uses `DocumentEditHistory` instead of `EditHistory`: a command mutates the model, then `BabylonJsonBinding.collect()` (`src/editor/BabylonJsonBinding.js`) returns patches `{ path, value }` for the values that changed — nodes (name, transform, visibility, material and skeleton — `materialId` / `skeletonId` together with `materialUniqueId` / `skeletonUniqueId` when the file has them, since the loader links by those first), vertex buffers, materials (`material.serialize()` key by key; textures only by their edited fields, since their serialized form changes while they load), cameras and lights (`serialize()` key by key), shadow generators (bias, normalBias, darkness), top-level file values (producer, clearColor, …), skeletons (name, ranges, bone name / `matrix` (bind) / `rest` / animation `keys`), animation groups (keys of each targeted animation, matched by target id and animation name; `from` / `to`); node transform channels driven by an animation are not compared (they show the playing pose, not the file value); bulky values are marked changed by wrapping `setVerticesData` / `setKeys` of the bound objects; vertices of a shared geometry (`geometryId`, `geometries.vertexData` — converted glTF models) are bound there, once for the meshes sharing it; values a comparison cannot see (a node position an animation drives) are written with `queuePatch`. Float32 values are written as the shortest decimal. The webview posts `{ type: 'patch', label, patches }`; the host writes each value in place (typed arrays as arrays, never as `{"0": …}` objects — `jsonText`) using the `JsonIndex` of the text (`src/utils/JsonIndex.js`: path → offsets, bulky arrays are leaves), inserting properties the file does not have yet, as one `WorkspaceEdit` (one undo step), and forwards the patches to the other 3D views.
  - *text → 3D*: `JsonDocuments` (`src/components/JsonDocuments.js`) keeps the index of every open `.babylon` text up to date and reports the changed paths; the host sends `{ type: 'applyPatches', patches }` (after 150 ms) and the binding applies them to the model; a change it cannot apply in place (structure changed, clip ranges) or that cannot be located reloads the model (`reloadModel` with `keepView`: camera, clip, frame and selection stay). While the text is not valid JSON the views keep the last model and show `documentError` ("File format error: … Fix the file in the source text or undo the changes.").
  - *compact ↔ raw*: compact edits are written into the raw text (the changed value is found by diffing against the last synced compact text, placeholders restored); raw changes are mirrored into the compact view by path (cut-out values stay placeholders; an unlocatable change re-collapses it). Saving the compact view saves the raw document; its `stat` mtime only changes when it is saved itself, so saves of the raw text are no conflict.
  - *Save with a check*: Ctrl/Cmd+S in these editors runs `babylon-editor.save` (`BabylonTextEditor.saveWithCheck`): the text is loaded in a separate scene of an open 3D view (or a temporary helper panel, `validate` / `validated` messages); if it does not load, a modal asks "Save Anyway". The menu, auto save and Save All use the plain save (VS Code has no API to cancel a text save).
  - `activate` returns `{ modelTree }` for integration tests (the tree items come from the webview, so they prove the model loaded).
- **Converted models**: `ConvertedModels` (`src/components/ConvertedModels.js`) is a `FileSystemProvider` for the `babylon-model` scheme (`babylon-model:<path>.babylon?<model file uri>`): reading converts the model file, saving converts the document back and writes the model file (once per session and format a modal lists what the format drops; `.gltf` / `.gltf2` cannot be written: Save As), an external change of the model file converts it again (VS Code reloads the document). The binary editor converts on open in its own webview (after `resolveCustomEditor` returned — VS Code shows the webview only then), opens the document with the text editor and closes itself. Conversions run in a webview through `WebviewTasks` (`src/components/WebviewTasks.js`: `validate` / `convertModel` / `exportModel` requests answered by `validated` / `converted` / `exported`, in an open 3D view or a temporary helper panel; editor panels pass their messages to `handleMessage`). In the webview `ModelConverter` (`src/editor/ModelConverter.js`) loads the model in a separate scene and writes it clean: objects without a name get one (`mesh1`), ids are unique per namespace, external textures are named by their path relative to the model folder (the format reads `rootUrl + name`), embedded ones keep `base64String` and get `textureLabel` names, `url`s and default-material references are removed, glTF group animations are not repeated on their targets, typed arrays (bone matrices) are written as arrays and numbers as shortest float32 decimals (`babylonJsonReplacer`), the text is formatted with small objects (keys) on one line, `producer` names the model file. `ModelConverter.writeBabylon` writes a scene that way without renaming (also used by Save As of the binary editor). `setupWebview` resolves resources of a converted document against the model folder and passes `payload.convertedFrom` (shown in the File view). **Save Model As…** (`babylon-editor.saveAs`, Ctrl/Cmd+Shift+S in these editors and in the binary editor, also in the `…` menu of the editor title; `ConvertedModels.saveModelAs` asks for the file) writes the model of the active document as `.babylon`, `.glb`, `.obj` or `.stl` — a model in the binary editor is written by its webview, as edited (`BabylonEditor.saveModelAs`). Node `Buffer`s from VS Code may be views of a pool: copy exact bytes (`toArrayBuffer`) before posting them.
- **Savable formats**: `.babylon` (the text, see above; `ModelSerializer` still has the `SceneSerializer` path), `.glb` (`GLTF2Export.GLBAsync` with `exportUnusedUVs`, else UVs of meshes without textures are dropped), `.obj` (`OBJExport`, keeps the `mtllib` reference; the `.mtl` is not rewritten), `.stl` (`STLExport`, binary/ASCII as the source). `.gltf`/`.gltf2`/`.ply`/`.splat`/`.spz` are view-only (inspector disabled). Format limits: OBJ/STL bake node transforms into vertices, STL drops names, glTF ignores transforms of skinned meshes.
- **Serialization scope**: `ModelSerializer.withModelOnly` (also used by the conversion) temporarily detaches from the scene everything not owned by the loaded `AssetContainer` (editor camera/light, the editor timeline group, Babylon's default material, highlight helpers) before running a whole-scene serializer.
- **Loaders**: the `.babylon` loader lives in `@babylonjs/core` (registered by the full `@babylonjs/core` import), all other formats come from `@babylonjs/loaders`. When importing Babylon partially, register `@babylonjs/core/Loading/Plugins/babylonFileLoader` explicitly.
- **Animations**: glTF provides `AnimationGroup`s. `.babylon` exports usually keep all clips on one timeline of bone animations plus named ranges (`skeleton.getAnimationRanges()`); `AnimationController` turns each range into a clip that plays a frame window of one shared `AnimationGroup` (no key copying), or the whole timeline as one clip when there are no ranges.
- **`BabylonDocument`** (`src/components/BabylonDocument.js`) wraps the raw `Uint8Array` file content and derives `type` (extension), `mimeType` (magic-byte sniffing in `determineMimeType`), and an exact copy of the bytes for `postMessage` (`getArrayBuffer`).
- **`VSCodeFSProvider`** (`src/components/VSCodeFSProvider.js`) implements Babylon's `IOfflineProvider` over `vscode.workspace.fs`, so Babylon can resolve external model resources (textures, `.bin`) through the VS Code filesystem instead of `fetch`. It is currently not wired in (it imports `vscode`, so it cannot run inside the webview).

## Smaller `.babylon` files

`BabylonOptimizer` (`src/utils/BabylonOptimizer.js`, host side, works on the parsed document): the setting `babylonEditor.minifyBabylon` (off by default) writes the `.babylon` documents the editor makes without line breaks — converted models (`ConvertedModels._convert`), Save Model As `.babylon` (`export` / `saveModelAs`, `minifiedIfSet`) and the two commands; the commands **Round Numbers…** (`babylon-editor.roundNumbers`: every number with a fraction to N decimals, 5 by default — decimals of the file units, so a model with small vertex units, e.g. scaled ×100 by its node, moves more) and **Reduce Animation Keys…** (`babylon-editor.reduceKeys`: keys the kept ones give back within a tolerance, 0.0001 by default — numbers, vectors and colors interpolated linearly, quaternions spherically; matrix keys only when equal to the one before, since Babylon holds matrices between keys (`Animation.AllowMatricesInterpolation` is off); the first and last key, keys at clip edges (ranges, animation group from / to) and animations with tangents or stepped keys stay) rewrite the document of the active tab (raw, compact or 3D view) as one undo step in the format of conversions (`BabylonTextEditor._optimize`), in the `…` menu of the editor title.

## AI Coding Principles

### 1. Study Existing Code and Reuse Analogues

Before implementing a task, carefully study the surrounding environment and existing codebase.
Find similar implementations, analyze them, and use these analogues as a basis for the current task.

If an analogue contains logic errors, does not handle certain edge cases,
or requires changes to be made universal enough to apply to the current task —
always propose fixes to those existing modules as part of the work.

### 2. Think Beyond the Current Task

Do not strictly limit reasoning to the immediate task.
Analyze adjacent modules and the overall project context to anticipate
how the created modules and their functions may be used in similar cases elsewhere.

### 3. Plan Before Complex Implementation

Before implementing a complex task, always create a plan and analyze it thoroughly multiple times.
Only begin implementation after the plan is approved — execute steps one by one,
verifying each step's result and checking for errors and compliance with the plan.

### 4. Prefer Universality Over Narrow Specificity

Sometimes it is worth sacrificing strict specificity and minimalism in favor of universality.
A more universal solution simplifies future use of the module,
allows it to be applied in different situations,
and eliminates code duplication.

### 5. Modular Code Organization

Write code in a modular way, grouping functionality by entity.
This makes code easier to study, remember, apply, and reuse.

- Do not split code into many tiny files.
- Do not overload methods and files with multiple unrelated responsibilities.
- Each logical block must be written as a separate function.

### 6. Anticipate All Behavioral Scenarios

Identify and account for all possible code behavior scenarios depending on incoming data.
Analyze: empty values, unexpected types, unavailable resources, boundary conditions.
Evaluate each scenario against the current task requirements and expected behavior —
not every edge case requires handling, but every case must be consciously considered.

### 7. Scoped Changes and Controlled Refactoring

Only change what is directly necessary for the current task.
Do not refactor unrelated code along the way — unless it is a pattern used by the current task
or inherits from it. In that case, do not silently refactor it either:
propose the fix for discussion and approval before applying.
Do not add unused abstractions "for the future" —
but design the code being written so that it can naturally be reused in future tasks.

### 8. State Assumptions and Uncertainties Explicitly

Never guess silently. If something is assumed rather than confirmed —
state it explicitly before proceeding.
Flag unclear requirements, ambiguous context, or missing information
so that decisions are made consciously, not accidentally.

### 9. Report All Bugs — Fix Only Task-Related Issues

Report every bug discovered; never ignore or fix them silently.
Inside current task: Fix it immediately.
Outside current task: Report it, pause the current task, and wait for a response before proceeding. Do not apply the fix without explicit approval.

### 10. Naming Conventions — Files vs Identifiers

A file is named after its primary export, using that export's casing:
**PascalCase** for classes/components (`components/BabylonEditor.jsx`,
`components/VSCodeFSProvider.js`), **camelCase** for single-function modules
(`utils/parseGlb.js`, `utils/determineMimeType.js`). Files without a single
named primary export (stylesheets, entry points, infrastructure modules) and
folders use **kebab-case** (`utils/jsx-runtime.js`, `scss/editor.scss`).
When in doubt, follow the convention already used in the target directory.
Do not rename existing files just to match this rule.

Identifiers in code (variables, functions, types, components, named exports) use
**PascalCase** for types/components/classes and **camelCase** for variables/functions —
matching their JavaScript semantics. Lowercase JSX tags are native HTML elements;
note that the custom JSX runtime does not render function components
(`<MyComponent/>`), so compose markup by calling functions that return JSX strings.

Conventional uppercase markdown files (`README.md`, `AGENTS.md`, `CLAUDE.md`,
`LICENSE.md`) keep their canonical casing.

### 11. No Comments in SCSS

Do not write comments inside `*.scss` files (no `//` and no `/* */`).
The selector tree itself (`.block { &__elem { ... } }`) is the documentation;
class names follow BEM and CSS variables are self-describing. If a rule needs
explanation, the explanation belongs in the component's JSX/markdown, not the
stylesheet. Move existing helpful notes out when you touch surrounding code.

### 12. Group SCSS Selectors by BEM Prefix

Do not write SCSS as a flat list of sibling selectors. Nest sub-elements
inside their parent block using `&-suffix` chains so each "section" collapses
to a single foldable group in the IDE. Apply to every BEM family
(`&__a`, `&__a-b`, `&__a-c` → nest `&-b` and `&-c` inside `&__a`). Modifiers of
the same element (`&--variant`), pseudo-elements (`&::before`), and descendant
overrides (`.card-header` inside the block) all go inside their owning selector —
never as siblings on the root level.
